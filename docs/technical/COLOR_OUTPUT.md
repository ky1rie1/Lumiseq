# Native export color audit — 2026-09-29

> Historical audit for the published integer pipeline. The 2026-10-02 development candidate adds pre-matrix float working pixels, PNG/TIFF ICC output and Display P3. See [current RAW quality](../RAW_QUALITY.md). The limitations and counts below describe the older implementation.

## Changes and delivered pixel contract

Native exports previously stored sRGB encoded pixels without a color profile declaration. Color managed receivers could therefore guess the wrong source space. The export pixel math and camera decoding parameters remain the same; the delivery files now declare the encoding they actually contain.

| Delivery path | Precision | Color declaration | Transparency |
| --- | --- | --- | --- |
| Native decoded RAW → PNG | 16 bits/channel | sRGB chunk, relative colorimetric intent; matching gAMA 45455 and standard cHRM primaries | Opaque RGBA16 |
| Native decoded RAW → JPEG | 8 bits/channel | Embedded 8784-byte original sRGB ICC v2 matrix/TRC profile | Opaque RGB8 |
| Browser Canvas → PNG/JPEG | 8 bits/channel | Browser manages encoding and file metadata; no native ICC promise | PNG can preserve edit transparency |

`getImageExportColorContract(document, format)` in `src/app/ImageExportService.ts` reports these paths from the same source resolver used by export. An undecoded RAW or unavailable develop source reports no deliverable bit depth. It does not change formats, dimensions, quality, or rendering.

The JPEG profile is generated by original MIT code in `src-tauri/src/raw/output_profile.rs`, from public ICC format definitions and sRGB constants. It contains D50-adapted primaries, the D65→D50 Bradford adaptation, a common 4096-entry sampled inverse piecewise sRGB curve, D50 white point, zero black point, and description/copyright tags. The three identical transfer curve tags share one payload. No downloaded ICC binary, darktable source, or RawTherapee source is copied.

## Evidence

- Before the fix, `native_deliveries_declare_srgb_color_metadata` failed because the PNG had no sRGB/gAMA/cHRM chunks. After adding PNG tags it failed because the JPEG had no ICC profile. After adding JPEG tagging it passed.
- The test inspects actual exported PNG chunks before image data, obtains the JPEG ICC through an independent decoder, interpolates the profile's sampled TRC against the analytic sRGB inverse near black and across midtones/highlights, and checks that adapted primaries sum to the tagged white point.
- `./scripts/run-cargo.ps1 test --lib raw::develop::tests`: 27 passed; one existing opt-in real RAW test ignored. Existing precision, JPEG quality, resizing, color, tone, masks, spatial, and rejection tests passed.
- `npx vitest run src/app/ImageExportService.test.ts`: 5 passed, including native PNG16/JPEG8, Canvas8, and unavailable RAW contracts. The new resolver assertions first failed on the absent helper.
- Independent interoperability: LittleCMS 2.17 through installed Pillow accepted the generated profile as “Lumiseq sRGB IEC61966-2.1”. A 65,536-color RGB grid (R/G steps 4, B steps 16) transformed from this profile to LittleCMS's standard sRGB at relative colorimetric intent produced maximum and mean 8-bit channel differences of **0**. This verifies profile interoperability, not camera color accuracy.
- The chart validator already accepts sRGB/gAMA/cHRM chunks with these exact standard values; PNG carries no iCCP/cICP profile requiring a validator change.

## Remaining limits and accurate terminology

LibRaw is configured with camera white balance before opening the file, output sRGB primaries, 16-bit channels, gamma `(1,1)`, `no_auto_bright=1`, and `bright=1`. The cached source is therefore **camera balanced, matrix converted, bounded linear sRGB**, not unbalanced sensor RGB and not an unbounded scene-linear wide-gamut buffer. The ICC profile describes exported pixels; it does not calibrate a camera.

The bundled LibRaw `convert_to_rgb_loop` clamps camera-converted channels to unsigned 16-bit values before our editor gets them. Sensor/channel saturation and sRGB gamut clipping cannot be reversed by later negative exposure, white balance, or profile tags. The no-auto-bright setting prevents additional histogram gain; it does not establish unrestricted highlight headroom. A future sensor-space or floating-point wider-gamut decoding pipeline would need coordinated decode, cache, preview, adjustment, and export changes.

Custom and automatic editor white balance are relative corrections after LibRaw's camera white balance and matrix conversion. The temperature control is not a measured as-shot illuminant replacement or an interpolated dual-illuminant DCP/ICC camera profile. The metadata `color_matrix` contains the first three columns of LibRaw `rgb_cam`, which maps camera RGB toward linear sRGB and has already been applied. It must not be presented or reapplied as a camera-to-XYZ matrix. Four-color-camera metadata would require its fourth column for a complete descriptive matrix.

Raw sensor metadata also remains approximate: the wrapper exposes per-channel `cblack` without spatial black patterns/global black-level reconstruction; repeats the reported maximum for every channel; infers sensor bit count from that maximum; and does not currently publish LibRaw daylight multipliers. These fields must not be used as a second calibration pass on the processed RGB buffer. No per-camera spectral/illuminant calibration, input DCP profile selection, user-selectable output profiles, soft proofing, or print conversion is added here.

The native exporter also resizes the final bounded sRGB encoded image. It does not claim linear-light resampling or wide-gamut preservation. Browser imports/Canvas paths remain constrained by the current browser color pipeline and 8-bit delivery. This audit does not independently establish monitor calibration or HDR/wide-gamut display accuracy.
